Gitチュートリアル③：リポジトリを作って基本コマンドを実践する

空のフォルダから練習用のリポジトリを作り、
init・add・commit・status・log・diffなどの基本コマンドを体験しましょう。
前回：Gitチュートリアル②：環境構築（インストールと初期設定）

目次

  1. 練習用リポジトリを作る
  2. 最初のファイルをcommitする
  3. git statusで状態を確認する
  4. git logで履歴を確認する
  5. git diffで変更内容を確認する
  6. 変更を取り消す
  7. .gitignoreで管理対象から除外する
  8. まとめ

練習用リポジトリを作る

まずは練習用のフォルダを作り、その中でGitリポジトリとして初期化します。

mkdir git-practice
cd git-practice
git init

mkdir <任意のフォルダ名>はフォルダを作成するコマンドです。
cd <任意のフォルダ名>は現在のフォルダ配下のフォルダに移動するコマンドです。
git initを実行すると、現在のフォルダの中に.gitという隠しフォルダが作られます。
このフォルダの中に、これから積み重ねていく変更履歴のすべてが記録されていきます。
フォルダ自体は普段どおり使えますが、Gitの管理下に入った状態になったということです。

NOTE 既に存在するGitHub上のリポジトリを手元にコピーしたい場合は、
git initではなく git clone URLを使います。clone操作は第5回で扱います。

最初のファイルをcommitする

適当なファイルを1つ作成してみます。

echo "# Git練習用リポジトリ" > README.md

echo "任意の文字列"は文字列を出力するコマンドで、>を使うことで、
指定のファイルに出力を保存できます。存在しないファイル名を指定した場合、新規作成されます。
作成しただけではGitの管理対象にはなりません。commitするまでの流れは次の3ステップです。 

# 1. 変更状態を確認する
git status

# 2. 変更をステージに追加する
git add README.md

# 3. commitとして記録する
git commit -m "READMEを追加"

ステージという中間エリア

Gitには、
「ワーキングディレクトリ（実際のファイル）」
「ステージ（commit予定のファイルを一時的に置く場所）」
「リポジトリ（commit済みの履歴）」
という3つの領域があります。
git addはワーキングディレクトリの変更をステージへ移す操作、
git commitはステージの内容をリポジトリへ記録する操作です。 

ワーキングディレクトリ  --git add-->  ステージ  --git commit-->  リポジトリ（履歴）

間にステージを挟むことで、「変更したファイルのうち、どれを今回のcommitに含めるか」を選べます。
複数の変更をしていても、関係のある変更だけをまとめてcommitすることが可能です。

POINT commitメッセージは「何をしたか」が一目で分かるように書きましょう。
「修正」「更新」のような曖昧な表現より、「READMEに使い方の説明を追加」のように具体的に書くと、
後から履歴を見返したときに役立ちます。

git statusで状態を確認する

作業中に迷ったら、まずgit statusを打つ癖をつけましょう。 「今どのファイルが変更されているか」「ステージに追加済みか」が表示されます。 

git status

試しにファイルをもう1つ追加・編集してから実行すると、状態の変化がわかります。

echo "console.log('hello');" > app.js
git status
# app.js が「Untracked files（未追跡）」として表示される

git add app.js
git status
# app.js が「Changes to be committed（ステージ済み）」に変わる

git logで履歴を確認する

app.jsもcommitしてから、これまでの履歴を確認してみます。

git commit -m "app.jsを追加"
git log

commitごとにハッシュ値・作者・日時・メッセージが表示されます。
1行ずつコンパクトに表示したい場合は、次のオプションが便利です。 

git log --oneline

ブランチの分岐まで含めて図で見たい場合は、次のように--graphを付けます（第4回で活躍します）。

git log --oneline --graph --all

git diffで変更内容を確認する

README.mdに1行追記してみます。

echo "practiceフォルダで基本コマンドを試しています。" >> README.md

commitする前に、具体的に何が変わったのかを確認したいときはgit diffを使います。 

# ワーキングディレクトリとステージ（＝直前のcommit）との差分
git diff

# ステージ済みの内容とcommit済みの内容との差分
git diff --staged

-で始まる行が削除された内容、+で始まる行が追加された内容を表します。
commit前の最終チェックとして習慣づけておくと、意図しない変更を含めてしまうミスを防げます。

変更を取り消す

作業していると、「やっぱり今の変更をなかったことにしたい」という場面がよくあります。
よく使う3パターンを紹介します。

コマンド できること
git restore ファイル名 ファイルを直前のcommitの状態に戻す（ステージ前の変更を取り消す）
git restore --staged ファイル名 git addを取り消し、ステージから外す（変更内容自体は残る）
git commit --amend 直前のcommitをやり直す（メッセージの修正や、追加のファイルを含め直す） 
# READMEの変更を取り消して直前のcommit状態に戻す
git restore README.md
NOTE git commit --amendは、すでにGitHubなどにpush済みのcommitに対して使うと 履歴の整合性が崩れる原因になります。まだ自分の手元だけにあるcommitに対して使うのが基本です。

.gitignoreで管理対象から除外する

ライブラリのインストールフォルダ（node_modulesなど）や、OSが自動生成するファイル、
パスワードなどの秘密情報を含む設定ファイルは、そもそもGitの管理対象に含めたくありません。
そうしたファイルやフォルダは、.gitignoreというファイルに記述しておくことで、
git statusやgit add .の対象から除外できます。 

# .gitignore の例
node_modules/
.env
*.log
.DS_Store
POINT すでに一度commitしてしまったファイルは、後から.gitignoreに追記しても自動では除外されません。
その場合はgit rm --cached ファイル名で履歴の追跡だけを止める必要があります。

まとめ

initでリポジトリを作り、add→commitの流れでcommitを積み、
status・log・diffで状態を確認する。これが日常的なGit操作の基本サイクルです。
次回はいよいよ、「ブランチ」を実際に作り、マージまで一通り体験します。
