リモートリポジトリとは

これまで扱ってきたのは、自分のPC上だけに存在するローカルリポジトリでした。
これに対し、GitHubなどインターネット上のサーバーに置かれたリポジトリを
リモートリポジトリと呼びます。
ローカルとリモートを紐づけておくことで、変更を送受信できるようになります。

既存のローカルリポジトリにリモートを紐づけるには、次のコマンドを使います。

git remote add origin https://github.com/ユーザー名/リポジトリ名.git

originは紐づけたリモートに付ける名前で、慣習的にこの名前が使われます。
登録済みのリモート一覧は次で確認できます。 

git remote -v

GitHub上にリポジトリを作ってcloneする

今回はGitHub上に空のリポジトリを新規作成し、それを手元にコピー（clone）する流れを試します。

  1. GitHubにログインし、右上の「+」から「New repository」を選ぶ
  2. リポジトリ名を入力し、「Create repository」を押す（READMEなどは追加しなくてよい）
  3. 表示されたHTTPSのURLをコピーする

手元のPCの、練習フォルダとは別の場所でcloneを実行します。

git clone https://github.com/ユーザー名/リポジトリ名.git

git cloneは、リモートの内容をまるごとダウンロードし、ローカルリポジトリとして使える状態にし、
さらにoriginという名前でそのリモートを自動的に紐づけてくれる、便利なコマンドです。

NOTE すでに手元にあるプロジェクトを後からGitHubに紐づける場合はgit remote add、
GitHub上のリポジトリを新しく手元にコピーしたい場合はgit clone、と覚えておくと迷いません。

push・pull・fetchの違い

ローカルとリモートの間で変更をやり取りするコマンドは、主に次の3つです。

コマンド 説明
git push ローカルのcommitをリモートに送る。
git fetch リモートの最新状態をダウンロードするだけで、
ローカルの作業内容にはまだ反映しない。
git pull fetchしたうえで、ローカルの今のブランチに自動的にマージ（またはリベース）する。
実質的にfetch＋mergeのショートカット。

試しに、cloneしたリポジトリでファイルを作ってpushしてみます。

echo "# サンプルリポジトリ" > README.md
git add README.md
git commit -m "READMEを追加"
git push origin main

GitHub側のページを開き直すと、pushした内容が反映されているのが確認できます。

POINT 複数人・複数端末で作業する場合は、作業を始める前にgit pullする習慣をつけておくと、
リモートとの食い違いによるコンフリクトが起きにくくなります。

追跡ブランチとgit push -u

ローカルのブランチとリモートのブランチを紐づけておくと（これを追跡ブランチの設定と呼びます）、
2回目以降はgit pushやgit pullだけで、どこに送受信するかをGitが自動判断してくれます。 

# 初回だけ -u（--set-upstream）を付けて紐づける
git push -u origin main

# 以降はこれだけでよい
git push
git pull

リベースの基礎

第4回で扱ったmergeは、分岐した履歴をそのまま残しつつ1本にまとめる方法でした。
これに対しリベースは、あるブランチのcommitを、別のブランチの最新地点に「積み直す」操作です。 

リベース前
C1 - C2 - C3           ← main
           \
            C4 - C5     ← feature

git switch feature
git rebase main

リベース後
C1 - C2 - C3                 ← main
             \
              C4'- C5'       ← feature（mainの最新地点の上に積み直された）

C4・C5はそのままコピーされるのではなく、C4'・C5'という新しいcommitとして作り直されます。
内容は同じでも、commitのハッシュ値が変わる点に注意してください。

NOTE リベース中にコンフリクトが起きた場合の解決方法は、マージのときとほぼ同じです。
目印を編集して内容を確定させたらgit addした後、git commitではなく
git rebase --continueで作業を再開します。中断したい場合はgit rebase --abortで元に戻せます。

リベースとマージの使い分け

merge rebase
履歴の見た目 分岐がそのまま残る 一直線に整理される
commitのハッシュ値 元のまま変わらない 作り直され、変わる
向いている場面 「いつ何を合流させたか」の事実を残したいとき 自分だけのブランチの履歴を、pushする前にきれいに整えたいとき
POINT すでに他の人と共有・pushしてしまったcommitをリベースすると、ハッシュ値が変わることで
相手側の履歴と食い違いが生じ、混乱の元になります。
「リベースはpushする前の、自分だけの作業に使う」と覚えておくと安全です。

プルリクエストの大まかな流れ

チーム開発では、mainブランチに直接pushするのではなく、作業用ブランチをpushしたうえで、
GitHub上の「Pull Request（プルリクエスト）」という機能を使い、
他のメンバーにレビューしてもらってからマージする、という流れが一般的です。
大まかな流れは次の通りです。

  1. 作業用ブランチを作る（git switch -c feature-xxx）
  2. そのブランチでcommitを積み、リモートにpushする（git push -u origin feature-xxx）
  3. GitHub上でPull Requestを作成し、変更内容の説明を書く
  4. 他のメンバーがレビューし、必要なら追加のcommitで修正する
  5. 承認されたらGitHub上のボタンでmainにマージする

これはGitHub側の機能であり、Gitコマンド自体に「プルリクエスト」という概念はありません。

まとめ・シリーズのまとめ

リモートリポジトリとのやり取りはclone・push・pull・fetchが基本です。
加えて、履歴を一直線に整理したいときの選択肢としてrebaseがあります。

全5回で一通りの基礎を扱いました。
ここから先は、実際の自分のプロジェクトでGitを使いながら、
必要な操作をそのつど調べていくのが一番の近道です。
ブランチの分岐やリベースの動きをアニメーションで視覚的に復習したい場合は、
Learn Git Branchingで 実際にコミットツリーを動かしながら練習してみてください。
