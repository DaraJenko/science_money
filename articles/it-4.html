今回は「ブランチ」を実際に作り、マージするところまでを体験します。

ブランチとは何か

ブランチとは、commitの流れを分岐させる「枝」です。
mainブランチの内容には変えずに、新しい枝の上で試行錯誤し、
適宜その枝の内容をmainに合流（マージ）させる、という進め方ができます。 

          C1 - C2 - C3   ← main
                     \
                      C4 - C5   ← feature（作業用ブランチ）

Gitのブランチの実体は、「どのcommitを指しているか」を記録した、名前付きのポインタです。
新しいブランチを作る操作は、フォルダをまるごとコピーするような重い処理ではなく、
ポインタを1つ追加するだけの一瞬で終わる操作です。この軽さのおかげで、
Gitでは気軽にブランチを切ることが推奨されています。

ブランチを作って移動する

前回作ったgit-practiceフォルダの続きから進めます。まず現在のブランチ一覧を確認します。 

git branch
# * main   ← *が付いているのが今いるブランチ

新しいブランチを作って、そのブランチに移動（切り替え）します。

# ブランチを作るだけ
git branch feature-login

# 作ったブランチに移動する
git switch feature-login

作成と移動を1コマンドで済ませることもできます。実務ではこちらの書き方の方がよく使われます。 

git switch -c feature-login
NOTE 少し前まではgit checkout -b feature-loginという書き方が主流でした。
checkoutはブランチ切り替え・ファイルの復元など複数の役割を兼ねていて分かりにくかったため、
現在はブランチ移動専用のgit switch、ファイル復元専用のgit restoreに役割が分けられています。
どちらの書き方でも動作するので、古い記事ではcheckoutも頻繁に登場します。

ブランチ上でcommitを積む

ブランチを切り替えたら、そのブランチ上でファイルを編集してcommitしてみます。

echo "ログイン機能を実装中" >> README.md
git add README.md
git commit -m "ログイン機能の作業を開始"

echo >はファイルの中身をすべて上書きするのに対して、
echo >>は末尾に追記するためのコマンドです。
ここで履歴をグラフ表示すると、mainとfeature-loginが分岐している様子が確認できます。 

git log --oneline --graph --all

試しにgit switch mainでmainブランチに戻ると、README.mdから先ほどの追記が消えています。
これは削除されたわけではなく、feature-loginブランチの方にだけ記録されている状態です。 

git switch main
cat README.md   # feature-loginでの追記が見えない

git switch feature-login
cat README.md   # 追記が見える

mainにマージする

feature-loginでの作業が完成したと仮定して、その内容をmainに取り込みます。
マージは「マージ先」に移動してから、「取り込みたいブランチ名」を指定して実行します。 

git switch main
git merge feature-login

今回のように、mainブランチ側でその後何もcommitしていない場合は、
mainのポインタをfeature-loginの位置までそのまま進めるだけで済みます。
これをfast-forwardマージと呼びます。 

マージ前
C1 - C2 - C3           ← main
           \
            C4 - C5     ← feature-login

マージ後（fast-forward）
C1 - C2 - C3 - C4 - C5   ← main, feature-login

一方、mainブランチ側でも別のcommitが進んでいた場合は、
両方の変更を1つにまとめた「マージcommit」が新しく作られます。
これを3-wayマージと呼びます。 

C1 - C2 - C3 --------- C6（マージcommit）  ← main
           \           /
            C4 - C5 --                    ← feature-login

コンフリクトを起こして解決する

同じファイルの同じ箇所を、mainとfeature-login側で別々に変更していた場合、
Gitはどちらを採用すべきか自動で判断できず、コンフリクト（衝突）が発生します。
実際に体験してみましょう。 

# mainブランチで1行目を変更してcommit
git switch main
echo "# Git練習用リポジトリ（メイン）" > README.md
git add README.md
git commit -m "mainでREADMEのタイトルを変更"

# feature側でも同じ1行目を別の内容に変更していたとする
git switch feature-login
echo "# Git練習用リポジトリ（ログイン機能ブランチ）" > README.md
git add README.md
git commit -m "featureでもREADMEのタイトルを変更"

# mainにマージしようとするとコンフリクトになる
git switch main
git merge feature-login

コンフリクトが起きると、該当ファイルの中に次のような目印が挿入されます。 

<<<<<<< HEAD
# Git練習用リポジトリ（メイン）
=======
# Git練習用リポジトリ（ログイン機能ブランチ）
>>>>>>> feature-login

<<<<<<< HEADから=======までが今いるブランチ（この場合main）側の内容、
=======から>>>>>>>までがマージしようとした側の内容です。
このマーカーを手作業（またはエディタのマージ支援機能）で編集し、
最終的にどちらの内容にするかを決めます。 

# 例：マージ側の表現を採用することにした場合
# Git練習用リポジトリ（ログイン機能ブランチ）

マーカーを削除して内容を確定させたら、通常のファイル変更と同じようにadd・commitします。

git add README.md
git commit -m "コンフリクトを解消してマージ"
POINT コンフリクトはGitの不具合ではなく、「自動で判断できないため人間に決めてほしい」という
正常な確認プロセスです。目印で挟まれた範囲を読み比べて、最終的にどう書きたいかを
決めれば大丈夫です。よく分からなくなったらgit merge --abortでマージ自体を取りやめ、
最初からやり直すこともできます。

不要になったブランチを消す

マージし終えて役目を終えたブランチは、消してしまって問題ありません。

git branch -d feature-login

まだmainに取り込んでいない変更がある状態で削除しようとすると、警告が出て削除を拒否します。
強制的にブランチを破棄したい場合は、大文字の-Dを使います（取り扱い注意）。 

git branch -D 未マージのブランチ名

まとめ

ブランチを作って作業を分岐させ、git mergeで本流に取り込む。
これがGitを使った並行作業の基本の流れです。コンフリクトも、仕組みが分かれば怖くありません。
次回は最終回として、GitHubなどのリモートリポジトリとのやり取りと、
履歴を整理するリベースの基礎を扱います。
